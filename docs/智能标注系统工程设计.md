# 智能标注系统工程设计

更新日期：2026-10-29

本文为概要设计。模块实现、数据库字段、接口协议、异常恢复与验收以 [智能标注系统详细设计与实现方案](./智能标注系统详细设计与实现方案.md) 为准。

## 1. 项目目标与边界

构建能够运行和演示的智能标注系统，以工程闭环为当前主线。用户为控制科学与工程学硕，实验室 GPU 型号与资源配额尚未确定，先采用公开数据集。文本和图像同等重要，第一版分别实现文本单标签分类和图像二维目标框检测。

完整流程：登录 → 创建项目和标签规范 → 导入数据 → 手工标注或提交自然语言任务 → 模型预标注 → 人工审核 → 导出已审核数据。

第一版必须具备用户身份、两类标注工作台、异步任务、模型插件、管理员 API 配置、Redis 缓存及关系库。MongoDB 在执行记录模块接入。训练、复杂反馈算法、客户端采集作为后续阶段，不成为基本标注流程的前置条件。

工程完整性可以支持学位论文的系统部分；学硕创新要求仍应结合导师和学院要求确认，功能完成本身不能保证满足研究创新要求。

## 2. 技术结构

采用模块化单体 API + 独立后台 Worker + 独立模型服务。初期避免拆分过多微服务。

| 层 | 方案 | 职责 |
| --- | --- | --- |
| 前端 | Vue3、TypeScript、Vite、Pinia | 项目、文本分类、图像框编辑、任务、模型和审核页面 |
| API | FastAPI、Pydantic | 身份授权、业务接口、输入与输出校验 |
| 数据访问 | SQLAlchemy、Alembic、PostgreSQL | 业务数据和迁移 |
| 后台执行 | Celery + Redis broker | 导入、批量标注、导出和模型启动任务 |
| 缓存 | 独立 Redis cache 实例 | 推理缓存、限流、短期进度 |
| 文档存储 | MongoDB | 脱敏 Agent 执行事件和诊断记录 |
| 文件存储 | 第一版本地卷，抽象存储接口 | 原始文件、图像、导出文件和模型文件 |
| 模型运行 | 按模型选用 Python 推理服务或兼容 HTTP 服务 | 与 API 分开加载和运行模型 |
| 部署 | Docker Compose | 主系统启动；本地模型按支持的配置启用 |

依赖版本在实际实现时固定，并验证目标操作系统和 GPU 支持，不将所有插件强制放进一个 Python 环境。

## 3. 页面与角色

页面：登录；项目列表和创建；项目数据列表；文本分类工作台；图像检测工作台；审核工作台；Agent 任务与运行记录；模型管理；管理员 API 配置；数据导入和导出记录。

| 角色 | 范围 |
| --- | --- |
| 管理员 | 用户、全局模型、API 配置和受支持的模型部署 |
| 项目负责人 | 项目成员、规范版本、模型选择、任务和导出 |
| 标注员 | 项目内数据访问、预标注查看和人工修改提交 |
| 审核员 | 项目内接受、退回和修正标注 |

所有权限由 API 校验，项目资源访问包含成员检查。后台任务继承受限的项目上下文，执行前检查资源仍可访问。登录使用安全密码哈希和短期访问凭证；退出与续期策略在实现时统一定义。

## 4. 两类工作台

### 文本分类

- 导入 UTF-8 CSV 或 JSONL，显式映射文本字段和外部样本 ID。
- 创建标签集合、标签解释、正反例和冲突规则。
- 显示原文、模型建议、来源及规则校验结果。
- 支持键盘选择标签、上一条/下一条、保存草稿和提交审核。
- 第一版限制为单标签分类，多标签和实体区间后续扩展。

### 图像目标检测

- 导入图片与可选的 YOLO/COCO 标签，保留来源记录。
- 使用 Canvas/SVG 实现框新增、移动、缩放、类别切换、删除和撤销。
- 保存原图尺寸，统一以原图像素坐标存储；显示缩放后坐标转换回原图。
- 保存前检查框边界、正宽高和合法类别。
- 支持补充漏检目标、删除误检框，以及明确标记“已检查，确实无目标”。空预测不等于人工确认无目标。

第一版项目采用一种任务类型；同一用户可同时维护文本和图像项目。图文配对数据与跨模态融合不在本阶段范围内。

## 5. 数据与版本

| 实体 | 主要内容 |
| --- | --- |
| users / projects / project_members | 身份、项目和角色 |
| datasets / dataset_versions | 导入批次、来源、版本和统计 |
| data_items | 文本或图像引用、内容摘要、外部 ID 和尺寸 |
| label_schema_versions | 标签 ID、名称、说明、规则、规范版本 |
| model_specs / model_deployments | 插件类型、检查点、能力、配置、运行状态 |
| provider_configs | 大模型服务地址、模型名、加密密钥、预算和限制 |
| jobs / job_items | 整体任务、逐样本状态、重试、用量、失败原因 |
| annotation_revisions | 每次模型预测或人工编辑的不可变修订 |
| review_decisions | 审核人、目标修订、接受/退回、时间和备注 |
| agent_runs | 结构化计划、版本引用、最终状态及记录索引 |
| exports | 选定版本、格式、文件位置和完成情况 |

预测、人工作业和审核结果分开保存。模型任务新增预测修订，不修改已审核修订。并发人工编辑采用版本检查，遇到冲突返回明确错误。

审核针对特定修订；已审核结果被编辑后，需要再次审核。导出任务固定规范、数据及标注修订清单，避免导出过程中混入新的修改。历史标签 ID 和历史规范保留，不通过删除标签破坏旧记录。

PostgreSQL 保存最终业务事实。MongoDB 保存辅助执行记录，通过 project_id、job_id、item_id 和 event_id 关联。核心任务状态不依赖 MongoDB 可用性。执行事件可通过关系库待发送记录异步写入 MongoDB，避免因为文档库短暂失败而丢失必要记录。

Redis 不保存唯一副本。推理缓存键包含项目、内容摘要、预处理配置、规范版本、检查点/部署版本、提示词版本和推理参数，更新模型或规则后自然失效。

## 6. Agent 的第一版职责

采用一个编排 Agent，通过受限工具处理标注任务。质量路由、权限校验和数据写入由明确的代码模块执行。

输入示例：“将本项目未标注的文本分成退款、物流、质量和其他，不确定的进入审核。”

结构化计划包含：project_id、dataset_version、task_type、label_schema_version、样本范围、plugin/deployment、复核策略、批量上限和调用预算。

流程：

1. 加载项目现有规范、可用模型和授权范围。
2. 将用户指令解析为结构化计划，保存输入、计划和版本引用。
3. 校验字段、模型能力、类别映射及预算；缺失关键标签含义时返回需要补充的信息。
4. 把合法计划转换为后台任务，分批调用预测工具。
5. 校验结果，保存预标注并按规则创建审核项。
6. 汇总成功、失败、待审核、成本与用时。

工具：读取数据、获取规范、查询兼容模型、批量预测、校验预测、创建审核项、查询任务状态、生成导出任务。

任务状态为 queued、running、cancel_requested、cancelled、succeeded、partially_failed、failed。审核是单独的业务流程，不让长期待审核占用 Worker。取消在批次边界检查；已完成结果保留。job_items 与唯一约束支持幂等写入；重试只处理尚未成功的条目。外部调用采用有界重试，记录可能重复调用产生的成本，不能承诺严格仅调用一次。

第一版提供可配置阈值和随机抽检，效果作为基线。模型分数含义不同，不直接比较文本分类概率和检测分数。检测复核同时考虑类别、定位和漏检；模型一致或没有预测框不作为绝对正确的依据。

## 7. 模型插件与部署

插件协议包括 metadata、validate_config、healthcheck、predict_batch。训练、部署、启动和停止属于独立的能力接口，插件可以不支持这些能力。

预测请求包含任务类型、数据引用、规范及模型版本。响应分别使用分类类别或检测框结构，共享 item_id、来源、版本、分数说明和错误字段。业务 API 不直接加载 GPU 模型；Worker 调用适配器访问模型服务。

| 插件 | 第一版接入要求 |
| --- | --- |
| BERT 分类 | 明确检查点、已训练分类头、tokenizer 和标签映射；原始 BERT 权重不能直接替代任务模型 |
| YOLO 检测 | 明确模型类别与项目类别映射；预训练模型不能识别任意新类别 |
| 远程语言模型 | 通过服务适配器调用；检查结构化输出、超时、限流和预算 |
| 本地 Qwen | GPU/CPU 条件明确后选择检查点与运行后端，验证与远程相同的业务协议 |
| DeepSeek 蒸馏模型 | 作为候选插件单独验证，依据任务质量和资源决定是否纳入演示 |

一键部署表示选择经过测试的模板，完成资源检查、权重准备、启动、健康检查和注册。模板固定入口与允许参数。部署状态包括 preparing、starting、ready、failed、stopped。管理员页面显示状态、日志和失败原因。模型不可用时任务明确失败或排队，模拟模型仅用于开发测试。

文本 LLM 与视觉模型按能力区分。图像升级处理先采用较强检测器；视觉语言模型可作为后续插件，不能因为具备图片描述能力就假定能精确定位。

## 8. 管理员大模型配置

配置字段：服务类型、base_url、model、加密 API key、超时、最大并发、允许参数、项目可用范围、用量和预算。编排模型与标注模型可分别选择。

密钥在服务端使用独立配置的主密钥加密；不返回给前端或写入普通日志。连接测试先检查认证和模型可用性，计费测试调用明确记录。预算采用提交与执行阶段的额度检查，避免并发任务重复使用相同剩余额度。

公开数据导入附带的真值保存为评估专用数据，不默认传入 Agent、提示词或预测请求。

## 11. 实施顺序与验收

| 阶段 | 交付与验收 |
| --- | --- |
| A：人工标注闭环 | 两类项目、身份权限、导入、文本分类、图像框编辑、审核、导出；可重新导入导出结果核对 |
| B：异步自动标注 | BERT 分类和 YOLO 检测适配器、任务进度、取消、恢复、缓存；失败条目可追踪与重试 |
| C：指令 Agent | 管理员配置远程 API；自然语言映射为可验证计划；保存预标注、版本和执行记录 |
| D：部署与文档库 | Compose 主系统、MongoDB 执行记录、受支持模型部署模板；按实际硬件验证本地 LLM |
| E：质量与论文扩展 | 独立公开评估集、人工用时、模型版本、质量—成本曲线；再决定反馈算法与训练模块 |

每阶段完成一个可演示闭环。首轮采用少量公开样本验证功能，不把数量当性能承诺。随后扩展样本量，记录吞吐、延迟、失败率和恢复情况。

关键验证：项目越权不能访问数据；框坐标缩放与导出正确；编辑后审核失效；后台重试不重复写入；更新规范后不复用旧缓存；模型失败有明确任务状态；导出只包含选定的已审核修订；评估真值不进入预测流程。

最终演示：管理员配置模型 → 分别创建文本和图像项目 → 导入公开样本 → 提交指令 → 查看自动标注与错误记录 → 人工修改审核 → 导出训练数据 → 替换兼容插件并观察版本变化。

## 12. 后续扩展

训练模块先支持固定数据版本与标签映射下的 BERT/YOLO 训练任务，再考虑语言模型微调。GPU 训练队列与在线推理隔离，并记录资源使用。

客户端资料采集使用已有批量导入接口提交数据，附带来源、采集时间、内容摘要和去重信息。桌面或移动端实现延后，不阻塞当前 Web 标注系统。

待落实的信息：毕业时间、实验室 GPU 配额、实际模型检查点、公开数据集与可用标签、是否要求数据库对比实验。基础人工标注、任务接口与插件协议不依赖 GPU 型号，可以先实施。
