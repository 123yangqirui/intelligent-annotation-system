# 智能标注系统：零基础逐模块开发路线

日期：2026-10-29

本文说明如何逐步实现系统。[详细设计与实现方案](./智能标注系统详细设计与实现方案.md) 是完整系统的目标架构；本路线用于安排学习与开发，每次只完成一个可以运行、检查的小目标。各阶段的文件和命令入口是开发安排，已经完成的部分见下方实现进度。

实现进度（2026-11-06）：基础前后端、数据库、权限、数据版本、文本和图像工作台、审核与导出、模型适配与 API 配置、后台任务、运维脚本和采集客户端已经加入。Agent 已增加，包含 SDK/HTTP 规划、业务工具、技能和运行恢复，见 [Agent 实现与使用说明](./Agent实现与使用说明.md)。模型部署与训练代码已提供，实际执行需要额外的模型、Docker 与训练环境；目前未验收 GPU 训练和真实供应商调用。

本文保留逐模块学习路线，描述每一步为什么要做。当前启动命令、源码导航和实际验收结果以 [实现与运行说明](./实现与运行说明.md) 为准，不能把下方的学习安排当作当前项目缺失功能清单。

## 1. 先理解开发顺序

推荐顺序：

```text
基础语法与环境
  → 最小前后端请求
  → 第一个数据库功能：项目创建与列表
  → 用户登录与项目权限
  → 数据与标签规范
  → 文本人工标注
  → 图像人工标注
  → 审核、版本与导出
  → 第一个真实模型预测
  → 后台批量任务
  → 管理员大模型 API 配置
  → 统一模型插件与部署
  → 自然语言 Agent
  → 完整部署、监控与恢复
```

测试从第一步开始，每完成一个功能检查一次。最终阶段补全自动化回归、性能和恢复测试，不把所有测试拖到最后。

前端也从第一步开始。每个业务模块都有对应的最小页面，功能正确后再改进交互和外观；不要全部后端完成后才尝试前后端连接。

模型推理、批量任务与模型部署是三个功能：先证明模型能预测一个样本，再管理批量任务，之后做服务启动与资源管理。Agent 最后接到这些已验证工具上。

## 2. 必要概念

| 概念 | 在本项目里的意思 | 最早在哪一步学习 |
| --- | --- | --- |
| 前端页面路由 | /projects 显示项目列表，/projects/:id 显示项目详情 | 阶段 1 |
| 后端 API 路由 | GET /api/v1/projects 返回数据，POST 创建数据 | 阶段 1–2 |
| HTTP / JSON | 浏览器发送请求，后端返回结构化数据 | 阶段 1 |
| 数据库表 | 保存用户、项目、数据与标注，重启后仍存在 | 阶段 2 |
| ORM | 用 Python 组织数据库读写，例如 SQLAlchemy | 阶段 2 |
| 数据库迁移 | 表结构变化有可重复执行的升级记录，例如 Alembic | 阶段 2 |
| 身份与权限 | 知道谁在访问，以及他能访问什么项目 | 阶段 3 |
| 组件 | 可复用的界面片段，例如标签列表和画框工具 | 阶段 4–6 |
| 模型推理 | 把样本送给模型，取回类别或目标框 | 阶段 8 |
| 后台任务 | 用户请求已受理后继续处理大量数据 | 阶段 9 |
| 模型部署 | 启动独立模型服务并检查是否可用 | 阶段 11 |
| Agent | 把自然语言转为计划，再调用现有接口/工具 | 阶段 12 |

例子：点击“创建项目” → Vue 收集名字 → fetch 发送 POST → FastAPI 校验 → SQLAlchemy 写 PostgreSQL → 返回项目 ID → Vue 显示新项目。

## 3. 每个模块的固定开发方法

每次按照下面顺序，不同时打开全部技术方向：

1. 写一句功能目标：例如“用户能创建项目，刷新后项目还在”。
2. 写验收动作：操作什么、应看到什么、失败应显示什么。
3. 定义最少数据字段和一个请求/响应例子。
4. 如果需要持久化，修改模型并创建数据库迁移。
5. 写业务校验与 API，用 /docs 先单独检查后端。
6. 写前端请求函数，再接最小页面。
7. 检查成功、失败、重启或刷新后的行为。
8. 更新 README 的运行说明和当前限制，保存 Git 提交。

不需要第一天完成全部表、全部页面或全部类。先实现完整设计里的最小集合，再通过迁移加字段。标签校验、项目权限、坐标、修订版本这些会影响数据正确性的规则，应在对应模块实现时完成。

## 4. 分阶段实施

### 阶段 0：开发环境和最少基础

**学习：**终端目录与命令、Git；Python 变量、列表、字典、函数、类与异常；JavaScript 对象、数组、函数、Promise、async/await；HTML 表单和简单 CSS。TypeScript 先掌握对象和函数参数类型，不学习复杂类型体操。

**实现：**核查电脑已有 Python、Node.js、Git；建立 frontend/、backend/ 与 README。数据库需要 PostgreSQL，可通过 Docker 或本地安装，选一种可用方式。Docker 若成为学习阻碍，先完成不依赖数据库的阶段 1。

**验收：**能启动和停止两个开发进程，知道错误输出在哪里，能保存一次 Git 提交。版本依据实际环境与官方快速开始要求确定。

### 阶段 1：打通最小前后端

**学习：**Vue 单文件组件、ref、按钮事件、fetch；FastAPI 的 GET、JSON、自动 API 文档；页面路由与 API 路由区别。

**实现：**

- 后端：GET /api/v1/health 返回 {"status":"ok"}。
- 前端：首页有“检查后端连接”按钮，显示连接成功或失败。
- 建立 / 与 /projects 两个页面路由，项目页面先说明功能目标，不铺设所有占位页面。
- 开发环境统一通过 Vite /api 代理访问后端；不要在每个组件写死后端地址。

**文件范围：**backend/app/main.py、frontend/src/App.vue、frontend/src/router/index.ts、frontend/src/api/client.ts、Vite 代理配置。

**验收：**后端 /docs 能调用接口；浏览器点击按钮成功；关闭后端后前端显示明确错误。正式部署同样计划 /api 同源访问；若使用跨域，再显式配置允许来源。

### 阶段 2：第一个数据库功能——项目

**学习：**表、主键、INSERT/SELECT、事务、SQLAlchemy Session、Alembic。

**实现：**PostgreSQL、project 表的最小字段 id/name/task_type/created_at；POST 与 GET /api/v1/projects；Vue 项目名称表单、类型选择、项目列表。

先选择 task_type 为 text_classification 或 image_detection；数据库类型与接口按目标设计保持一致。数据库连接放环境配置，创建第一份迁移。

**验收：**创建项目后列表显示；刷新浏览器、重启 API 后数据仍存在；空名字和非法任务类型被拒绝。

**阶段限制：**此时只有本机开发数据和无身份的演示接口，不部署给他人使用。在阶段 3 绑定用户后，清理或由迁移管理命令显式关联这批开发项目。

### 阶段 3：登录与项目权限

**学习：**密码哈希、access token、请求头、401/403、用户与项目成员关系。

**实现：**users/project_members；管理员创建账号；登录、当前用户、刷新、退出；项目创建绑定用户；列表只显示有权限项目。前端增加登录页和统一凭证处理。

按详细设计建立短期 access token 与安全 refresh 会话，但可按“登录成功 → 受保护接口 → 刷新退出”分成三个小任务。不要自己设计密码加密算法；使用可靠库。

**验收：**未登录不能访问项目；用户 A 不能读用户 B 的项目；退出后不能刷新旧会话；配置与日志中没有明文密码。

### 阶段 4：数据与标签规范

**学习：**上传、表单校验、文件对象、JSON、表关联、不可变版本。

**实现顺序：**先手工录入几条文本和两三个标签 → 增加小文件 JSONL/CSV 导入 → 增加图片上传 → 再支持图片包与标签文件。创建规范草稿和发布版本，数据项绑定项目，工作状态绑定规范版本。

**前端：**项目详情、数据列表、标签编辑、导入进度/错误页。首批只用少量公开样例，不先下载整个大数据集。

**验收：**合法数据导入可浏览，错误行可定位；图片尺寸正确；发布后的标签规范不直接修改；评估真值与编辑数据用途分开。

### 阶段 5：文本人工标注

**学习：**组件状态、保存请求、修订、乐观并发、草稿与提交区别。

**实现：**原文显示、标签选择、保存草稿、上一条/下一条、提交；annotation_revisions 与 work_states。先做点击保存，再做自动保存和快捷键。

**验收：**刷新后标签还在；未知标签被拒绝；同一工作版本并发保存有明确冲突；重复发送同 operation_id 不重复创建结果。

### 阶段 6：图像人工标注

**学习：**画布事件、缩放、平移、坐标变换、组件与业务数据分离。

**实现顺序：**显示图片 → 画一个框 → 保存/重载 → 多框 → 类别选择 → 移动缩放 → 删除/撤销 → 平移缩放 → 无目标确认。采用 Konva，业务存原图 xyxy，不把屏幕坐标直接存数据库。

**验收：**不同画布缩放下重载框位置一致；越界和无面积框被拒绝；真正无目标图片可明确确认；多框修改不影响其他框。

文本和图像在完整系统中同等重要。先做文本只是降低第一次实现交互的难度，下一阶段立即完成图像，不把图像无限推后。

### 阶段 7：审核、历史与导出

**学习：**审核角色、修订来源、状态机、固定快照、格式转换。

**实现：**提交具体修订、接受/退回、修订历史、编辑后重新审核；文本 JSONL 导出；图像 YOLO 导出，随后 COCO。每次导出固定样本与修订清单。

**验收：**未审核数据不进入默认已审核导出；编辑后旧审核不可作为当前结果；导出再导入标签和框一致。

**里程碑：**到这里得到一个完整人工标注系统。没有任何模型，也能独立演示和使用。

### 阶段 8：第一个真实模型预测

**学习：**模型加载、推理、tokenizer、类别映射、检测框与模型分数。

**实现顺序：**

1. 用独立脚本给一条文本或一张图片预测，确认检查点、类别与输出。
2. 建立薄 Adapter，将结果变成统一分类/框结构。
3. 用单样本接口或小任务调用 Adapter，保存为预标注。
4. UI 显示建议，用户采用后生成独立人工修订。

先完成一个真实模型，之后接另一任务模型；检查点要支持项目类别。BERT 原始权重不是已经可用的分类器；YOLO 预训练检查点不能检测任意自定义类别。

**验收：**脚本和页面都能得到真实预测；无效结果被拒绝；预测不覆盖人工结果。长时加载与推理在独立模型服务中运行，不能长期堵塞业务 API。

### 阶段 9：批量后台任务

**学习：**Celery、Redis broker、任务 ID、轮询、幂等、取消与重试。

**实现：**任务受理返回 202/job_id；固定 job_items；小批次执行；任务页显示进度；取消停止领取新项；失败重试；DB 支撑派发恢复。先完成小批样例，再增加数据量。

Redis broker 为队列，Redis cache 为缓存：先接队列；等推理正确后再加推理缓存。初期没有性能问题时不要先开发所有缓存。

**验收：**关闭页面不影响任务；Worker 中断可恢复；重复派发不重复写结果；任务结束后计数正确；取消保留完成项。

### 阶段 10：管理员大模型 API 配置

**学习：**服务端 HTTP 客户端、超时、密钥、usage、限流与预算。

**实现：**先用服务端配置完成一次真实调用 → 增加管理员配置表单 → 密钥加密与脱敏 → 项目授权 → 调用限额与预算预留。编排模型和标注模型分别选择。

先把大模型作为普通标注插件使用，不立即构建 Agent。API key 不进浏览器，用户不能随意改模型 base_url。

**验收：**可修改配置并测试；错误密钥有明确错误；预算不足不调用；超时费用未知有记录；前端和日志看不到 key。

### 阶段 11：模型插件和部署

**学习：**接口协议、配置版本、健康检查、容器、资源边界。

**实现：**把已经运行的两个模型整理成统一 Adapter/ModelSpec/Deployment；支持能力发现与类别映射；然后增加固定模板的启动停止和健康状态。已运行远程服务注册可以先做，本地 Qwen/DeepSeek 等 GPU 条件明确再适配。

MongoDB 在此时或阶段 12 接入执行事件；此前必要任务状态和日志已在 PG 保存。双数据库职责不能混淆，最终标注不在两个库独立维护。

**验收：**更换兼容模型不用改标注页面；历史来源完整；模型启动失败不显示可用；重复部署消息不会创建多个实例。

### 阶段 12：Agent

**学习：**结构化输出、工具调用、计划校验、状态机、上下文和权限边界。

**实现：**将自然语言解析为“项目、规范、数据范围、模型、预算、审核策略” → 后端校验 → 调用既有任务工具 → 页面展示计划、缺失信息、执行结果。

工具只开放已验证功能：读取规范、查询兼容模型、创建预测任务、查询状态、创建审核任务和导出。禁止任意运行 Python/shell。默认合法计划直接执行已经授权的操作，必要信息缺失时再询问补充。

**验收：**自然语言得到正确任务；模型编造标签/模型 ID/项目时被拒绝；任务总结来源于真实计数；规划失败不影响手工任务表单。

### 阶段 13：完整部署、监控与恢复

**学习：**Docker Compose、Nginx、环境配置、迁移、日志、备份和健康检查。

**实现：**打包已有服务；空环境初始化；健康状态；必要日志与审计；PG/对象文件/加密密钥备份；恢复演练；E2E 与失败场景回归。GPU 模型独立配置，不假定 macOS 开发环境直接支持 Linux CUDA 容器。

**验收：**另一套干净环境按照 README 可以启动；文本与图像两个流程运行；重启不丢数据；从备份恢复后能读旧标注和导出。

### 阶段 14：质量研究与客户端扩展

基础系统稳定后，增加固定数据版本下的训练和评估、反馈路由，以及后续客户端采集。质量指标、人工时间和模型用量从前面阶段开始保存，不等最后再补数据。

## 5. 遇到错误的排查顺序

```text
页面没有结果
  → 浏览器开发者工具：请求有没有发出？
  → Network：地址、方法、请求体、状态码是什么？
  → /docs：同一个接口单独调用能否成功？
  → 后端日志：校验、权限、数据库还是模型报错？
  → 数据库：实际有没有保存？
  → Worker：任务有没有领取，模型有没有返回？
```

先定位出错层，再修改。不要看到页面没更新就同时重写 Vue、数据库和模型。

## 6. 第一轮只做哪些文件

只安排阶段 1 的最小文件：

```text
backend/
  app/main.py              # 一个健康接口
  pyproject.toml           # 依赖与运行配置
frontend/
  src/App.vue              # 页面布局
  src/router/index.ts      # 首页、项目页面
  src/api/client.ts        # HTTP 请求入口
  src/views/HomeView.vue   # 连接状态按钮
  src/views/ProjectsView.vue
  vite.config.ts           # /api 开发代理
README.md                  # 如何启动、停止与检查
```

暂时不写 Agent、模型部署、全部数据库表、复杂状态管理和整套管理员页面。阶段 1 验收完成后，阶段 2 只增加项目表、迁移、项目接口和项目列表，继续沿同一个可运行系统推进。
